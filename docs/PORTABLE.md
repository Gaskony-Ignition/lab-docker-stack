# Running this anywhere — macOS, Windows, Linux

The whole stack builds itself from a clone. What this machine needs:

- **Docker Desktop** (macOS, Windows) or **Docker Engine + Compose** (Linux)
- **git**

That is the complete list. No node, no python, no particular version of bash, no
Playwright install, no GNU coreutils, no make.

```bash
git clone <this repo> && cd Ignition-Demos-Stack

./wd bootstrap        # macOS, Linux, or Windows under Git Bash
.\wd.cmd bootstrap    # Windows PowerShell  (in cmd.exe the .\ is optional)
```

**A plain clone is the whole story. There are no submodules and nothing asks for
credentials.** That is worth stating because it was not always true, and the way
it failed is the reason the styling is vendored now.

A submodule pinned to a **private** upstream repo would prompt for
credentials on clone. At a console that is the normal Git prompt and it works.
It does not work anywhere there is nothing to prompt -- over SSH, from a
scheduled task, from CI -- and the failure names the wrong thing:

```text
fatal: Unable to persist credentials with the 'wincredman' credential store.
fatal: could not read Username for 'https://github.com'
Failed to clone 'styles-template' a second time, aborting
```

**The outer clone succeeded and only the submodule failed**, so you were left
with a checkout that looked complete and deployed no projects -- on a machine
whose owner might have no access to that repo at all.

The styling is now committed here, in two halves: `ignition/themes/` (ten
gateway config resources) and `ignition/projects/Themes/` (690 style classes).
Both are generated by `scripts/gen-themes.py` from a checkout of upstream, which
is a **maintenance** action for when upstream corrects a colour -- not something
a clone ever runs. The only thing this stack still fetches over the network is
the third-party modules, and those are hash-checked against `modules.manifest`.

First run builds a toolbox image (a few minutes) and then works through sixteen
steps: environment files, certificates, third-party modules, the shared network,
the containers, module installation, the projects, the database connection, the
Gateway Network, EAM, MQTT over TLS, store and forward, and the redundant pair.
It is safe to re-run — every step checks before it acts — and it prints exactly
what did not complete rather than burying it.

Afterwards the ordinary loop is the same commands as always, one word longer:

```
./wd status                    what is running
./wd deploy PROJECT=Site1      validate, stage, copy, scan
./wd redundancy-status         the redundant pair
./wd bash                      a shell inside the toolbox
./wd -- node scripts/ign-gw.js api --gateway local --path /data/api/v1/redundancy
```

### On a blank Ubuntu VM: `scripts/blank-vm.sh`

The two prerequisites above still have to come from somewhere, and on a fresh
VM that is a dozen commands with one trap in the middle. `scripts/blank-vm.sh`
is the whole path — Docker from Docker's own apt repo (not `docker.io`, which
carries no Compose *plugin*), git, the GitHub CLI, an interactive `gh auth
login`, the clone, and `./wd bootstrap`.

Open it on github.com and paste it into a file on the VM; it lives in the repo
it clones, so it cannot bootstrap itself, and no `curl | bash` line is offered
because a private raw URL needs a token in it. It re-runs safely: every step
checks before acting.

**Run it as root or as a sudo user — both work**, which matters because some
VM images only ever hand you root (DigitalOcean, Hetzner, Vultr) while others
hand you a sudo user (AWS, Azure, GCP). Root is in fact the simpler path: no
sudo, no docker group, and `hosts-setup.sh` writes `/etc/hosts` directly
because it tests `[ -w ]` before reaching for sudo. Everything then belongs to
root, which is self-consistent — `wd` runs the toolbox as
`--user $(id -u):$(id -g)`, so as root that is `0:0` and the repo it writes
into is root's too.

**What you must not do is mix them.** Bootstrap as root and then drive the
stack as a normal user and the `.env` files, the CA and the deployed projects
are all root-owned, so `wd` cannot rewrite them. Pick one and stay with it.

**The trap the non-root path exists to step over** is `usermod -aG docker`.
Group membership is fixed at login, so adding yourself to a group does nothing
for the shell you are already in — a script that installs Docker and then calls
it gets `permission denied on /var/run/docker.sock`, which reads exactly like a
broken install. The usual advice, log out and back in, is no use to a script
that has not finished. As root none of this applies.

**And there is no single mechanism for borrowing the group**, which cost a run
on a real VM. `sg docker -c '<command>'` is the classic answer and `sg` is
**not always installed**: on current Ubuntu it comes from `util-linux-extra`,
having moved there from `login`, so a minimal cloud image does not have it and
"it is in the base system" is no longer true. So the script tries, in order:
nothing at all (root, or a shell that logged in with the group), `sg`, then
`sudo -u "$USER" -g docker`. It picks between them **by running docker**, not
by testing for the binaries, so whatever it selects is known to work.

The first version reported that failure as *"docker is installed but not usable
even with the group applied — check the daemon"*, and every word of that was
wrong: the group was fine, the daemon was fine, and `sg` did not exist. It sent
the reader to `systemctl status docker`, which reports everything healthy, and
the trail ended there. **Name the mechanism that failed, not the subsystem you
assumed it implicates.**

It also probes Docker's repository for your release's codename before writing
the apt source. A brand-new or interim Ubuntu exists for months before Docker
cuts a matching suite, and the failure is a poor one to read: `apt-get update`
succeeds, because the repo answers and simply has no such suite, and the
install then fails with `Unable to locate package docker-ce` — which looks like
a typo or a missing repo rather than a release Docker has not reached yet. When
the codename is absent it falls back to the newest suite that exists and says
so.

## Why a toolbox container

The *stack* was always portable — named volumes, container-name addressing,
every host port overridable from a `.env`. The *tooling* was not, and it failed
in ways that are invisible until somebody else tries.

| What | Where it broke |
|---|---|
| `declare -A`, `mapfile` | bash 4 features. macOS ships bash **3.2**, so four scripts died with a syntax error on a line that reads fine. |
| `find -printf`, `xargs -r` | GNU-only. BSD `find` on macOS has neither. |
| Playwright | loaded from a hard-coded path under one person's home directory, and a ~400 MB per-machine install besides. |
| Gateway credentials | read from a machine-wide file outside the repo. A fresh clone had no such file and every script died at the first API call. |
| `make` | not present on Windows at all. |
| Container paths | Git Bash rewrites `/work` into `C:/Program Files/Git/work` on the way into `docker run`, silently, with no error. |
| Relative bind mounts | `./certs` is resolved by whatever runs `docker compose`, and from inside the toolbox that path is not the host's. Docker does not fail on a missing bind source — it **creates an empty directory**, so the broker crash-looped and Postgres came up healthy with none of its databases. |
| `TZ` | The toolbox exported one, and compose prefers the shell environment to `.env` — so it overrode `TZ=Australia/Adelaide` in nine files and started the gateways in another timezone. Linux got `UTC` from a `${TZ:-UTC}` default; Windows got **empty**, which reads as UTC too. |

Every one of those is fixable in the scripts, and doing so is a tax forever:
each new script has to be written for the union of three platforms, and the
failure mode is always *works here, breaks on the machine you cannot see*. So
the scripts run in one place instead. The host only has to be able to run
Docker.

The toolbox is a **sibling** of the stack, not a parent. It talks to the host's
Docker daemon through the mounted socket, so `docker compose up` from inside
starts containers *outside*, beside it. It joins `backbone` for the same reason
the gateways address each other by container name: from in there the hub is
`http://ignition:8088` on every machine, and the host port mappings — which
differ per machine, and do on the dev VM — stop mattering entirely.

### Two addresses per gateway

`.gateways.env` is generated by `make-env.sh` from `.secrets.env` and the ports
in `stacks/*/.env`. It lists every gateway twice:

```
local.url=http://ignition:8088          # container name, used inside the toolbox
local.hosturl=http://localhost:29088     # host port, used by a browser and by native runs
```

`WD_TOOLBOX=1` (set by the image) decides which applies. Getting this wrong is
not subtle in effect but is very subtle in appearance: inside the toolbox,
`localhost` is the toolbox, so a host-port URL reaches nothing and every script
reports the gateway as down.

The file is **gitignored and generated** — delete it and `./wd env` rebuilds it.
No password is stored twice.

## What each platform needs to know

### macOS

Nothing beyond Docker Desktop. The bash-3.2 and BSD-`find` problems are why the
toolbox exists; none of them can reach you through it.

### Windows

**Type `.\wd.cmd`, with the leading `.\`, in PowerShell.** PowerShell does not
run commands from the current directory, so a bare `wd.cmd bootstrap` fails with
`The term 'wd.cmd' is not recognized` — which reads as a missing file sitting
right there in the listing. (PowerShell does at least suggest the fix in its
error.) In `cmd.exe` either form works.

`wd.cmd` is a separate file from `wd` rather than a wrapper, because cmd.exe is
the one shell that is always present — Git Bash usually is, and "usually" is how
this whole problem started. It also sidesteps MSYS path rewriting entirely,
since cmd does not touch the arguments.

If you prefer Git Bash, `./wd` works there too: it sets `MSYS_NO_PATHCONV=1`
itself, so the volume mounts arrive as written.

`.gitattributes` forces LF on every text file regardless of your `core.autocrlf`
setting. Without it, a checked-out shell script gets CRLF endings and fails
inside a Linux container with `bad interpreter: /usr/bin/env bash^M` — which
reads as a missing interpreter, and is, just not the one named. Batch files stay
CRLF, which is what cmd expects.

Docker Desktop proxies `/var/run/docker.sock` into Linux containers even though
the host is Windows, so the socket mount is the same line on all three
platforms.

> **Run it from a terminal you are logged into.** Driving Docker Desktop over
> SSH, or from a scheduled task, or from a CI agent running as a service, cannot
> reach a registry: the Windows credential store needs an interactive logon
> session, and without one *every* pull fails with
>
> ```text
> error getting credentials - err: exit status 1,
> out: `A specified logon session does not exist. It may already have been terminated.`
> ```
>
> including `docker pull hello-world`. Everything else works — `docker ps`,
> `logs`, `exec`, `compose up` on images already present — so the failure looks
> oddly specific to building the toolbox. It is not this repo, and setting
> `DOCKER_CONFIG` at an empty config does not help; Windows falls back to its
> built-in helper regardless. If you need a headless build, pull the base
> images from an interactive session first, or build the toolbox elsewhere and
> `docker load` it.

### Linux

`wd` passes `--user $(id -u):$(id -g)` so files written into the bind-mounted
repo are owned by you rather than by root — a root-owned `.env` or deployed
project outlives the container and is a nuisance to undo. It then adds the
Docker socket's group, without which the CLI inside answers "permission denied
while trying to connect to the Docker daemon socket", which reads like Docker
not running.

Neither is done on Docker Desktop, and that is correct rather than an omission:
the VM maps ownership already, and a host uid means nothing inside it.

## Host ports

Container-internal ports never change. The host side is what collides, and every
one of them is overridable in the stack's `.env`:

**Every published port is in 29000–29999, and that is the whole point.** The
stack used the obvious numbers — 8088, 5432, 1883 — and the obvious numbers are
the ones something else already has. 29xxx is also *below* the ephemeral range
(Linux allocates outbound sockets from 32768 up), so a published port cannot
collide with an outgoing connection either — which is the failure that makes
"just pick a high number" wrong.

| service | default | variable |
|---|---|---|
| hub gateway | 29088 / 29043 / 29041 (OPC UA) | `IGNITION_HTTP_HOST_PORT`, `IGNITION_HTTPS_HOST_PORT`, `IGNITION_OPCUA_HOST_PORT` |
| redundant backup | 29388 / 29343 / 29341 (OPC UA) | `BACKUP_HTTP_HOST_PORT`, `BACKUP_HTTPS_HOST_PORT`, `BACKUP_OPCUA_HOST_PORT` |
| edge 1 | 29188 / 29143 / 29141 (OPC UA) | `EDGE1_HTTP_HOST_PORT`, `EDGE1_HTTPS_HOST_PORT`, `EDGE1_OPCUA_HOST_PORT` |
| edge 2 | 29288 / 29243 / 29241 (OPC UA) | `EDGE2_HTTP_HOST_PORT`, `EDGE2_HTTPS_HOST_PORT`, `EDGE2_OPCUA_HOST_PORT` |
| edge 3 (isolated, MQTT demo) | 29588 / 29543 / 29541 (OPC UA) | `EDGE3_HTTP_HOST_PORT`, `EDGE3_HTTPS_HOST_PORT`, `EDGE3_OPCUA_HOST_PORT` |
| edge 4 (isolated, MQTT demo) | 29688 / 29643 / 29641 (OPC UA) | `EDGE4_HTTP_HOST_PORT`, `EDGE4_HTTPS_HOST_PORT`, `EDGE4_OPCUA_HOST_PORT` |
| pair front door | 29404 (HAProxy stats) | `HA_STATS_HOST_PORT` |
| demo console control plane | 29485 | `WD_CONTROL_HTTP_HOST_PORT` |
| proxy | **80 / 443** + 29081 admin | `NPM_HTTP_HOST_PORT`, `NPM_HTTPS_HOST_PORT`, `NPM_ADMIN_HOST_PORT` |
| Postgres | 29432 (loopback only) | `POSTGRES_HOST_PORT` |

Change one and re-run `./wd env` so `.gateways.env` picks up the new `hosturl`.
Nothing else needs to know — the gateways reach each other by container name.

> **80 and 443 are the exception, and they stay put.** They are what
> `https://ignition.test` *means*, and that name is the redundancy
> demonstration's front door — one origin in front of both halves of the pair,
> without which a failover leaves the browser stranded on a standby that serves
> no session. A port there would have to be typed into every URL, which is
> exactly what the hosts file and the proxy exist to avoid. If something else on
> the machine already owns 80, move *that* if you can; moving the proxy costs
> you the redundancy demo's front door and the signed-in gateway buttons with it.

## The third-party modules

`modules/` is gitignored: these are vendor binaries, some licensed, and putting
~140 MB of them in the repo would both bloat every clone forever and
redistribute software that is not ours to redistribute.

`scripts/get-modules.sh` runs as step 3 of bootstrap and tries three things in
order — already present and hash-correct, a URL from
`scripts/modules.manifest`, then `$MODULES_MIRROR/<filename>`. **Everything is
verified by SHA-256**, downloaded or not: a module is a signed binary the
gateway will execute, and "the download returned 200" is not the same as "this
is the file the stack was tested against".

**All four fetch themselves** — a fresh clone needs nothing by hand:

| module | source |
|---|---|
| Embr Charts | GitHub release asset, MIT |
| MQTT Engine | `releases.inductiveautomation.com` — needs a `Referer` (below) |
| MQTT Transmission | as above |
| Architecture Builder | GitHub release asset from its author, MIT |

The Architecture Builder was recorded for months as "Ignition Exchange resource
2693, needs an account". That is a **different artefact** — a project export for
Ignition 8.1 by another author. The module is published openly by its own author
at `ia-tgoetz/ArchitectureBuilderReactFlow`, which this repo already named in
`scripts/upstream.pins` and `docs/ARCH-BUILDER.md`; only the manifest still
pointed at the Exchange. Its release asset is called plain
`ArchitectureBuilder.modl` with the version only in the tag, so the manifest's
filename column is what puts the version back.

**The Cirrus Link modules looked un-fetchable for months, and the evidence was
misleading.** `curl` got `403 AccessDenied` from
`releases.inductiveautomation.com` while a browser downloaded the same URL
without signing in, which reads as "the file needs credentials". It does not —
the host is hotlink-protected, and the only thing separating the two requests is
the `Referer` header a browser sends and `curl` does not. Any
`inductiveautomation.com` referer returns 200; a foreign one returns 403. The downloads page even offers a **"Skip form and download
directly"** link pointing at these exact URLs, so nothing here is a bypass — the
form is optional and always was. `get-modules.sh:referer_for()` sends the header
for that host and no other.

Worth remembering beyond this repo: **when a browser can fetch a file and `curl`
cannot, diff the request headers before concluding it is authenticated.**

**To share them with the team without putting binaries in git**, host the files
somewhere everyone can reach and set `MODULES_MIRROR` to that base URL:

```bash
MODULES_MIRROR=https://files.example.com/ignition-modules ./wd bootstrap
```

The hash is still checked, so a mirror cannot drift from what was tested.

Without them the stack still runs. What you lose is Site 2's Sparkplug road on
the Store & Forward page (Site 1 goes over the Gateway Network and is
unaffected) and the Architecture tab. Styling, EAM distribution and redundancy
use none of them.

**Module versions are pinned to the Ignition version.** A module built for 8.1
will not load on 8.3; the gateway logs a version mismatch and carries on without
it, which looks like the module simply not working. When the gateways move to a
new Ignition version, `scripts/modules.manifest` changes in the same commit.

## Running the scripts natively

Still supported on Linux, and still how the maintainer works day to day — the scripts are
unchanged, they just need node, python3, bash 4+ and a Playwright install on the
host. `.gateways.env` carries `hosturl` for exactly this: without `WD_TOOLBOX=1`
every script addresses the gateways by host port instead of container name.

`./wd` is the supported path for everyone else, and the one the documentation
assumes.

## What a release needs to work here

A release is **the repo at a tag** — see [RELEASING.md](RELEASING.md). Nothing is
attached to it, because nothing needs to be: everything is either committed or
fetched by a committed script. What a machine has to supply for itself is
exactly the list in *What is deliberately not portable* below, plus the two
things the tag cannot carry:

| what | how it arrives | why it is not in the release |
|---|---|---|
| Docker, git | installed on the host | the only two prerequisites |
| the toolbox image | `./wd` builds it from `tools/toolbox/` when its tag is missing | a local image with no registry; building it is one command and a few minutes |
| the third-party `.modl` files | `./wd -- scripts/get-modules.sh`, hash-checked | licensed vendor binaries, not ours to redistribute |
| `.env` files and `.secrets.env` | `./wd env`, with generated passwords | a password in a release is a password on every machine |
| the local CA and its leaves | `./wd certs`, then `make trust-ca` on the host | machine-local on purpose |
| the `.test` names | `scripts/hosts-setup.sh` (may need sudo) | they belong to this machine's hosts file |
| gateway state | built by `./wd bootstrap`, by API, from scratch | see below — a backup carries another machine's addresses into this one |
| machine-side steps a release assumes | `./wd migrate`, run for you by `make update` | a Docker network, a generated token, a Postgres trigger — none of them files |
| settings this machine keeps | `.demo-settings.env`, from the committed template | the whole point is that an update cannot reach it |

So taking a release onto a machine that has never seen this repo is:

```bash
git clone <this repo> && cd Ignition-Demos-Stack
git checkout v1.0.0          # or leave it on main and let `make update` move it
./wd bootstrap               # builds everything, and baselines the migrations
make trust-ca                # once, on the host itself
```

and onto a machine that already runs it, `make update`.

**A migration is never how a fresh machine is built.** `bootstrap` constructs
every end state a migration exists to reach, so it records them all as applied
without running them (`scripts/migrate.sh --baseline`). Migrations only ever
carry an *existing* machine forward.

## What is deliberately not portable

**The local certificate authority.** `stacks/npm/certs/` is generated per
machine and gitignored. Sharing a CA
would mean sharing the ability to mint certificates that every machine trusting
it would accept. Each clone makes its own; nothing depends on them matching.

**`.secrets.env`.** Generated on first `./wd env`, unique per machine, never
committed. Two people cloning this repo end up with different gateway passwords,
which is correct.

**Gateway *state* is rebuilt, not copied.** No `.gwbk` moves between machines.
Bootstrap builds the database connection, the Gateway Network pairing, the EAM
registration, the MQTT configuration, the historian, the security zone and the
redundant pair from scratch, by API, every time. That is slower than restoring a
backup and it is the only version that stays honest: a backup carries one
machine's addresses, certificates and passwords into another machine, and the
failures that causes surface days later.

## The stack manifests (`stacks/*/stack.meta`)

Every stack describes itself in a flat `KEY=VALUE` file, and everything that
needs a list of stacks derives from those files: start order, `make status`,
`.gateways.env`, the proxy hosts, the TLS SANs, the hosts-file names, volume
seeding, and which gateways bootstrap wires up. Adding a stack means adding a
folder -- see "Adding a stack" in docs/ARCHITECTURE.md.

The grammar is deliberately as dumb as possible, because it has exactly two
parsers and neither is allowed to be clever:

- `scripts/lib.sh` -- bash 3.2 `sed` (macOS ships 3.2; pieces of this run on
  the raw host, not in the toolbox)
- `scripts/hosts-setup.ps1` -- PowerShell 5 `Select-String` (a Windows host
  has no bash at all)

So: one `KEY=VALUE` per line; whole-line `#` comments only; values are bare
tokens (`[A-Za-z0-9._:/-]+`, non-empty) except `STATUS_NOTE`, which may be
double-quoted free text with no embedded quotes; optional keys are OMITTED,
never left empty; LF only (pinned by .gitattributes -- a CRLF line would land
a broken entry in a hosts file silently). The closed keyword set, the
per-KIND required fields and every cross-file claim are enforced by
`make validate`, which is what makes the dumb grammar safe.
