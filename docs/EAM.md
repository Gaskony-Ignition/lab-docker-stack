# EAM — pushing projects from the hub to the edges

The demonstration this repo is built around: change a Site project on the hub, push it
to an Edge gateway over the Gateway Network, and have the customer watch a completely
different-looking application appear on the edge.

EAM configuration is **gateway state, not repo state**. None of it is file-based, so
none of it is in git — this document is the procedure, and the gateway is the record.
That split is deliberate: see rule 4 in [../CLAUDE.md](../CLAUDE.md).

## What is already true

The Enterprise Administration module ships in the base `inductiveautomation/ignition`
image — verified present on 8.3.8, no download needed. The hub commissions as
**standard** edition (33 modules on 8.3.8) and the spokes as **edge** (22 modules).

> The upstream README says "Edge loads about 20 modules, Standard about 94". The 94 is
> stale — 8.3.8 consolidated modules and a standard gateway now reports 33. Use the
> relative difference as the signal, not the absolute number.

## Automated so far

```bash
scripts/ign-modules.sh <gateway>                           # install .modl files
node scripts/ign-gw.js commission  --gateway <name>        # clear the licence wizard
node scripts/ign-gw.js gan-connect --gateway local-edge1   # outgoing connection
scripts/ign-gan.sh certs                                   # peer certs, both directions
node scripts/ign-gw.js gan-approve --gateway local         # incoming connections
scripts/ign-gan.sh incoming                                # independent check
```

`--gateway` names a stanza in `.gateways.env` (`local`, `local-edge1`,
`local-edge2`), which `scripts/make-env.sh` derives from `.secrets.env` — both
gitignored, both generated by `make env` -- keeping credentials in a
machine-wide file outside the repo would be exactly the dependency that is
invisible until someone clones this and every script dies at the first API
call.

Both spokes reach `Connected`, and no gateway restart is needed at any point.

**Certificate approval is a file move, not a UI action.** An SSL Gateway Network
connection stays FAULTED until each side approves the other's certificate, and the only
clue is buried in the log:

```
java.security.cert.CertificateException: No approved certificate could be found in
the certificates folder! To allow connection, the server certificate
'CN=<host>:8060, OU=GatewayNetwork, ...' must be approved
```

"The certificates folder" is literal:

```
data/config/local/ignition/gateway-network/<client|server>/security/pki/
    rejected/        seen, not accepted
    trusted/certs/   approved
```

`client/` holds certs of gateways this one dials **out** to; `server/` holds certs of
gateways that dial **in**. A spoke needs the hub in `client/`, the hub needs each spoke
in `server/`. `scripts/ign-gan.sh certs` moves them and fixes ownership; driving the
UI's per-row menu proved unreliable — it reports success and leaves the cert rejected.

**Approving the incoming connections goes through the REST API, not the DOM.** Once
certificates are trusted the spokes appear under Incoming Connections with SECURITY =
*Pending Approval*. Neither the per-row menu nor the bulk checkbox could be driven
headlessly — both report success and change nothing, which is indistinguishable from
having worked. The grids are divs rather than tables and the row menus render in portals,
so there is nothing stable to click.

The call underneath is stable, and finding it took three wrong turns worth recording:

1. **The obvious endpoint does not exist.** The page *reads* its rows through
   `GET /data/api/v1/resources/list/ignition/gateway-network-incoming`, so the natural
   guess is that it writes them back through `PUT /data/api/v1/resources/…`. That path
   404s. Approval has its own endpoint.
2. **The real call is in a lazily-loaded chunk** that is not in the page's importmap and
   is not in `ia-gateway.js` or `IgnitionGatewayLib.js`, so grepping the obvious bundles
   finds nothing. Trace it instead:

   ```bash
   TRACE_ALL=1 node scripts/ign-gw.js explore \
     --gateway local --path /app/network/gateway/connections/incoming --trace
   ```

   then read `/res/sys/js/gateway/IncomingConnectionsPage.chunk.bundle.js`:

   ```text
   PUT /data/api/v1/gateway-network-incoming/toggleApproval/<remoteId>/<bool>
   ```

   `remoteId` is `config.connectionId` (`edge1|<uuid>`), URL-encoded. No request body.
3. **Every write needs an `X-CSRF-Token`.** Without it 8.3 answers **403** on a fully
   authenticated session. This is the same 403 that made `POST /data/api/v1/trial` look
   like a permissions problem and sent the trial reset down the click-the-button route.
   The token comes from `GET /data/app/session` as `csrfToken`; the SPA attaches it to
   every mutation.

`gan-approve` re-reads the list afterwards rather than trusting the status codes, and
`scripts/ign-gan.sh incoming` reads the same state off disk as an independent check.

## 1. Gateway Network first

EAM rides on the Gateway Network, so pair the gateways before touching EAM.

Spokes dial **out** to the hub; the hub never initiates. On each edge gateway
(`http://localhost:29188`, `http://localhost:29288`):

**Config → Networking → Gateway Network → Outgoing Connections → Create**

| Field   | Value      |
|---------|------------|
| Host    | `ignition` |
| Port    | `8060`     |
| Use SSL | on         |

Use the hostname **`ignition`**. Inside a container `localhost` is that container
itself, and 8060 is the GAN port, not the web port. The GAN port is deliberately not
published to the host — the spokes reach it over `backbone`.

Then approve them on the hub at **Config → Networking → Gateway Network → Incoming
Connections**. They appear as **`Ignition-Edge1`** and **`Ignition-Edge2`**, from the
`-n` arguments in each spoke's `command:` block. Without those they would identify
themselves by container ID. The hub is **`Ignition-Standard`**.

> Supersedes earlier advice (≤01/08/2026) that an established gateway's system name must
> never change. It *is* the gateway's identity on the Gateway Network, but a rename
> applies **live** through the `ignition/system-properties` resource — the GAN channel
> manager restarts itself, no gateway restart — and costs less than feared, verified
> 03/08/2026 when all three gateways were renamed:
>
> **In Docker there is a second authority.** The image's `-n` argument re-applies on
> **every container start**, not just at commissioning — a `docker restart` quietly
> reverted both renamed edges to their old names. Rename in compose *and* via the API,
> and apply compose changes with a **recreate** (`up -d`), never a restart.
>
> - The hub's **incoming-connection record renames itself in place**, keeping its UUID
>   and its `Approved` status. Certificates are keyed by hostname, not system name, so
>   trust survives too.
> - **EAM does need re-pairing**: each agent re-registers under its new name (and against
>   the hub's new serverId), so run `eam-setup --role agent --reregister` on each edge,
>   `eam-agents --approve` on the hub, and delete the old agent records. Task
>   `targetGateways` reference agents by name and must be updated.
> - The old serverIds linger in the hub's *status* page as `NotConnected` ghosts until
>   its next natural restart. Cosmetic — there is no API to forget them.

## 2. Controller and agents

```bash
node scripts/ign-gw.js eam-setup  --gateway local       --role controller
node scripts/ign-gw.js eam-setup  --gateway local-edge1 --role agent
node scripts/ign-gw.js eam-setup  --gateway local-edge2 --role agent
node scripts/ign-gw.js eam-agents --gateway local --approve
```

EAM's install mode is not a wizard — it is a **singleton config resource**, which is why
this is scriptable:

```text
GET /data/api/v1/resources/singleton/com.inductiveautomation.eam/module-settings
PUT /data/api/v1/resources/com.inductiveautomation.eam/module-settings   body: [resource]
```

`installMode` is `NotInstalled | Controller | Agent`. Read-modify-write, sending the
record's `signature` back so the endpoint can refuse a stale overwrite.

**An agent names its controller by Gateway Network `serverId`**, not by hostname, and the
form validates it against the live peer list. So read it from
`/data/api/v1/gateway-network/gateways` rather than constructing it from the hub's name —
`eam-setup --role agent` discovers it automatically when there is exactly one connected
peer, and takes `--controller <serverId>` when there is more than one.

The controller's `datasource` is nullable, so it runs without a database; agent event
history simply has nowhere to land. Fine for a demonstration.

**Agents register, then wait for approval** — the same two-step as a Gateway Network
incoming connection, and a separate act from it. Registration happens on the agent's
`sendStatsInterval` (45s by default), so the controller's agent list is empty for up to a
minute after `eam-setup`. Approval is
`POST /data/eam/api/v1/approve-agent/<name>`.

An agent that shows up but never goes green is almost always the Gateway Network
connection, not EAM — check step 1 before debugging EAM itself.

**A GAN channel can wedge without retrying.** Seen 03/08/2026 after a hub restart: the
edge's websocket pinged successfully, then errored `Could not decode response header` /
`Metro-RunDownloadThread`, and sat at `Defined_NeverConnected` indefinitely — no retry,
nothing further in the log. The cure is a bounce of the edge's outgoing-connection
resource, no restart: `PUT /data/api/v1/resources/ignition/gateway-network-outgoing`
with `enabled: false`, then again with `enabled: true`. Connected within seconds.

### Two transitions that bite

**Controller → Agent is rejected.** The PUT comes back **400 with an empty body**, which
looks like a malformed request and is not. Install mode has to pass through
`NotInstalled` first; the reverse direction is fine. `eam-setup` inserts that step
automatically.

**The controller caches an agent's licence state from registration and never refreshes
it.** An agent that registers while its gateway trial is expired keeps reporting
`Trial Expired:Agent` indefinitely — the Agents page shows `0 / 2` connected and every
task against it fails with `Attempt 1: Trial expired on agent` — *even though the agent's
own `/data/api/v1/trial` says `expired: false` with an hour left*. Resetting the trial is
not enough on its own. Force a re-registration:

```bash
scripts/ign-trial.sh reset --all
node scripts/ign-gw.js eam-setup  --gateway local-edge1 --role agent --reregister
node scripts/ign-gw.js eam-agents --gateway local --approve   # re-registering needs re-approval
```

That is what took both agents from `Trial Expired:Agent` to `Connected` here. Note the
second line: a re-registered agent comes back as **Pending** and must be approved again.

Order matters on a cold start — reset the trials *before* pointing the agents at the
controller, and none of this arises.

## 3. Pushing a project

Hub → **Enterprise Administration → Tasks → Create Task → Send Project**, or through the
API:

```bash
# create
POST /data/api/v1/resources/com.inductiveautomation.eam/eam-tasks   body: [task]
# run it now  --  owner is the SHORT module name "eam", not "core" and not
# "com.inductiveautomation.eam" (both of those 500 with "No resource handler registered")
POST /data/eam/api/v1/eam-tasks/force/eam/<url-encoded task name>?retry=true
# what happened
GET  /data/eam/api/v1/eam-tasks/history
```

The task is an **extension-point resource**, so it nests as
`config.profile` + `config.settings` — and `scheduleMode` goes in `profile`, not
`settings`. `"Immediate"` runs it on save; without a schedule the force call fails with
*"Task could not be rescheduled to run immediately"*.

```json
{
  "name": "Send Site1 to Ignition-Edge1",
  "config": {
    "profile": { "type": "eam_sendProject", "scheduleMode": "Immediate", "scheduleDetails": "" },
    "settings": {
      "targetGateways": ["Ignition-Edge1"],
      "sourceProject": "Site1",
      "flattenProjectsKey": true,
      "targetGroups": [], "controllerIsTargetKey": false,
      "maxConcurrentAgents": 0, "selectedGateway": ""
    }
  }
}
```

`flattenProjectsKey` **is** the "Include inherited project resources" checkbox. Every task
type and its default settings can be read from
`GET /data/api/v1/resources/type/com.inductiveautomation.eam/eam-tasks` — the
`extensionPoints` array lists all eleven (`eam_sendProject`, `eam_backup`,
`eam_restart`, …) with their exact setting keys, so there is no need to guess any of them.

| Field    | Value                                       |
|----------|---------------------------------------------|
| Source   | `Ignition-Standard` (the hub)                |
| Project  | `Site1`                                      |
| Targets  | `Ignition-Edge1`                             |
| Schedule | On demand, or on a change trigger            |

### The inheritance trap — tick "Include inherited project resources"

**An Edge gateway runs exactly one project.** It is created at commissioning, is named
`Edge` by default, and cannot be removed. Three projects deployed to
`ignition-edge1`'s filesystem still start only `Edge` — the other two sit on
disk and return HTTP 404, with nothing in the log to explain it.

So the obvious plan — send `Toolbox_Styles`, then send `Site1` on top — **cannot work on
Edge**. Two projects is one more than Edge has room for.

EAM has the answer built in. On the Send Project task:

> ☑ **Include inherited project resources**
> *If checked, the selected project and any inherited resources will be combined into a
> single project on the target agents.*

That flattens `Site1` + `Toolbox_Styles` into one project at push time. The hub keeps the
clean template/override split; the edge receives a single self-contained project, which
is all it can hold.

**It lands under the name `Edge`, not `Site1`.** The pushed project overwrites the edge's
own project and arrives with `parent: ""` — its title still reads "Site 1 - Northern
Plant", but the URL is `/data/perspective/client/Edge/demo`. Screenshotting `Site1` on an
edge returns *Sorry, but project "Site1" does not exist*, which reads exactly like a
failed push and is not one.

**Tick that box for every push to an Edge agent.** Without it you are sending a
three-file project whose parent will never exist on the target.

### An edge shows nothing until its Panel session is given to Perspective

A fresh edge answers `/data/perspective/client/Edge/demo` with **Sessions Exceeded** on a
healthy trial, because an Edge gateway has one Panel session and `visualizationName` in
`ignition/edge-system-properties` decides which module gets it — the default is `VISION`.
The full diagnosis is below under *"Sessions Exceeded" on Edge with 0 running sessions*.

```
make edge-visual     # sets visualizationName=PERSPECTIVE on every edge
```

`scripts/ign-edge-visual.sh`, idempotent, run by `bootstrap` at step 11b, and checked by
`make verify-demos` — because the pack comparison is happy either way, so an edge can hold
exactly the right theme and be unable to show it. Measured 31/08/2026: one PUT, no
restart, both edges went straight from the splash to the full dashboard (122 components,
zero errors).

> **The lesson an easy mistake here teaches: check what you did NOT vary.**
> A controlled experiment can look conclusive and still prove nothing --
> two throwaway gateways, same image, same trial, the same project,
> `IGNITION_EDITION=edge` refusing and `standard` rendering. **Both probes
> inherited the same `VISION` default**, so the variable being isolated was never the
> cause. Worse, the answer was already in this file, resolved 01/08/2026 after a day of
> wrong hypotheses, and rediscovering it cost most of a session.
>
> Two rules earned. When an experiment isolates a variable, check that what you did *not*
> vary is not the cause: two gateways sharing a default are not a control. And read the
> doc for the thing you are debugging before building an experiment — `docs/` knew this.

**What actually lands is not a new project — it overwrites `Edge`.** Verified here on
01/08/2026. After pushing `Site1` to edge1, the edge still has exactly one project,
still called `Edge`, and its `project.json` reads:

```json
{ "title": "Site 1 - Northern Plant", "inheritable": false, "parent": "" }
```

`parent` is empty because the ancestry has been folded in: 2,258 resources on the edge
against Site1's own 3, including all 1,104 style classes and the `session.custom.style`
pin. So the edge's one-project limit is respected by *replacing* its contents, and the
project keeps the name the edge commissioned it with. Do not go looking for a `Site1`
project on the edge — there will never be one.

The trade-off is that each push is then the full ~2,250 resources rather than three
files. Still a good story — the *authoring* stays a thin per-site override, and one
central template change redeploys to every site — but do not claim the wire transfer is
kilobytes. It isn't, on Edge.

A standard-edition target has no such limit, so hub→hub pushes can keep the two projects
separate and stay small.

## 4. The demonstration loop

**The headline act — change the theme once, push it everywhere:**

```bash
# 1. One line in the template's script library:
#    ignition/projects/Toolbox_Styles/ignition/script-python/toolbox_styles/code.py
#    CHOSEN_PACK = "glass-aurora"
make deploy PROJECT=Toolbox_Styles      # or just save in the Designer
#    Both hub sites re-theme on their next page load. Nothing is pushed yet.

# 2. Push, from the page itself:
#    http://localhost:29088/data/perspective/client/Site1/admin
#    "Push BOTH edges", or one edge at a time to show them changing separately.
```

Both edges land on the identical theme while Line 1 and Line 2 stay obviously
different screens — different KPIs, gauge, trend shape and range, batches and
alarms. That contrast is the point: the shared thing is unmistakably shared, and
the per-site thing is unmistakably not.

**The buttons use `system.eam.runTask`, not the REST route.**

    system.eam.runTask("Send Site1 to Ignition-Edge1", "eam", True)

`owner` is `"eam"` for EAM's own tasks; the third argument re-runs a forced task
that failed. It is **Controller-only** — the same buttons on an edge
report the failure in the status line rather than doing nothing. No credentials
are involved, which is the only reason a Perspective button can push at all. From
outside the gateway, `scripts/` still uses
`POST /data/eam/api/v1/eam-tasks/force/eam/<url-encoded name>?retry=true`.

**Where the theme lives, and why it is not a session prop.** A child project's
`session-props` resource **replaces** the parent's rather than merging with it, so
a value the template sets there never reaches a Site that has its own session
props — and both Sites need their own, for their line data. Verified the hard way:
dropping `style` from `Site1`'s props left `session.custom.style` undefined and
the whole page rendered unstyled. Each Site therefore binds `session.custom.style`
to `runScript('toolbox_styles.chosen_pack()')`. An inherited script library is
shared *and* a project resource, so EAM carries it.

The tasks are `scheduleMode: OnDemand`, so they persist and sit in the hub UI ready
to run in front of a customer.

Available style packs:

```
cmms-workorder   crm-cloud       dark-analytics  dark-control-room
enterprise-material  erp-fiori   finance-ledger  glass-aurora
high-contrast-field  isa-101-high-performance    legacy-panel
minimal-mono     projectops-agile  saas-light    terminal-retro
wms-scanner
```

## Edge limitations worth knowing before you demo

These shape what you can promise a customer, so know them before you are in front of one.

**One project, always.** Created at commissioning, named `Edge` by default (renameable),
cannot be removed, and a second one will not start. Verified here — see the inheritance
section above. This is why the flatten checkbox is mandatory.

**Third-party modules mostly do not run.** *"Third party modules will not run on an Edge
Gateway, with the exception of any third party module explicitly stated by a product,
such as the Edge IIoT product."* It is a platform allowlist, not a compatibility problem,
and there is no way to sideload around it. Consequences here:

- **Cirrus Link MQTT Transmission** is one of the allowlisted exceptions — MQTTS from
  edge to hub is fine.
- **Embr Charts is not**, and lifting that needs a licence approval per gateway. Its
  components render as black `embr.chart.apex-charts not found` boxes on both edges,
  permanently -- so the dashboard drops Embr entirely: the OEE donut and
  throughput trend are `ia.chart.simple-gauge` and `ia.chart.xy`, which
  ship inside the Perspective module and so render identically on hub and edge. Nothing
  on the dashboard is third-party any more. If you add a component, check it is stock
  before assuming the edges will draw it.

**Reduced module set and session count.** 22 modules against the hub's 33, and Perspective
sessions are capped. Fine for a demonstration; not for a room where everyone opens it on
their phone.

> **"Sessions Exceeded" on Edge with 0 running sessions — the visualization property.**
> Resolved 01/08/2026 after a day of wrong hypotheses, and automated since:
> `make edge-visual` sets it, `bootstrap` runs it, `verify-demos` checks it. An Edge gateway runs exactly one
> visualization system, chosen by the `ignition/edge-system-properties` singleton — and
> when `visualizationName` is `VISION`, **Perspective's session limit is zero by
> design**, trial or not. Both edges here commissioned with `VISION`. The refusal page
> says *"the number of running client sessions has exceeded the permitted number"* with
> zero sessions running, nothing in the log, and a healthy trial — nothing points at the
> property.
>
> Diagnosis path worth keeping: the client shell is served 200 and decides nothing — the
> refusal comes from the handshake, `GET /data/perspective/hello/<project>/<n>`, which
> returns `license: {permitted: false, reason: "sessions-exceeded"}`. That reason string
> led (via `javap` on `PerspectiveLicenseState` in the Perspective module jar) to the
> actual rule: *scope Designer → always permitted; Edge + Vision → max 0; Edge trial
> otherwise → max(licensed, 2)*.
>
> The fix is one word, applied live with no restart:
>
> ```bash
> # read: GET  /data/api/v1/resources/singleton/ignition/edge-system-properties
> # fix:  PUT  /data/api/v1/resources/ignition/edge-system-properties
> #       config.visualizationName: "VISION" -> "PERSPECTIVE"
> ```
>
> The enum (from `EdgeSystemProperties$Visualization` in gateway-api) is exactly
> `VISION | PERSPECTIVE`. Wrong hypotheses ruled out on the way, each by test: not EAM
> (edge2 had no push, behaved identically); not leaked screenshot sessions (5 minutes of
> silence, same refusal); not an expired trial; not a licence state latched at module
> startup (Perspective restarted under a healthy trial and still refused).

Edge also creates an `edge` tag provider at commissioning. Leave it alone.

## What to check when a push does nothing

1. Is the Gateway Network connection green **both ways**? Incoming on the hub, outgoing
   on the edge.
2. Did the task actually run? Hub → Enterprise Administration → Tasks → history.
3. Was the task flattened? A pushed `Site1` without its inherited resources is inert,
   because Edge has no room for the parent project alongside it.
4. On the edge, is the project enabled? A pushed project arrives enabled, but a previous
   failed push can leave a disabled shell behind.
